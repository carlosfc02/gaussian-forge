# GaussianForge Usage Guide

This document is the detailed operational guide for GaussianForge. The README is intentionally short; this file explains the pipeline, scripts and common workflows.

## Execution Model

GaussianForge is designed to run end-to-end on Linux or WSL2:

- The web backend runs with the Python environment in `web/backend`.
- The frontend runs with Node/npm from `web/frontend`.
- Heavy compute runs in Docker containers.
- Local viewers run through a Linux/WSL Docker service.
- Runtime data lives under `data/`, `jobs/`, `logs/` and `models/`.

The PowerShell viewer scripts remain as legacy helpers, but the supported web flow does not require Windows binaries.

## Required Software

Install on Linux/WSL:

- Python 3.10+
- Node.js 22 LTS and npm
- Docker and Docker Compose
- ffmpeg
- NVIDIA drivers and GPU-enabled Docker
- WSLg or X11 for local viewers

On native Linux with X11, viewer containers may need:

```bash
xhost +local:docker
```

## Container Services

Build all services:

```bash
docker compose build sam2-seg colmap gaussian-splatting sugar viewer
```

Services:

- `sam2-seg`: SAM 2 segmentation container.
- `colmap`: CUDA-enabled COLMAP container.
- `gaussian-splatting`: official 3DGS training container with local masked-loss patches.
- `sugar`: official SuGaR training container.
- `viewer`: Linux SIBR Gaussian Viewer container.

All generated artifacts are mounted from the repository, mainly under `/data` inside containers.

## Web Application

Backend:

```bash
cd web/backend
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
uvicorn app.main:app --reload --host 0.0.0.0 --port 8000
```

Frontend:

```bash
cd web/frontend
npm install
npm start
```

Open:

```text
http://localhost:4200
```

The web UI provides:

- project creation from video upload,
- project state detection,
- simple full-pipeline execution with presets,
- advanced stage selection and guided options,
- live logs,
- cancellation,
- generated asset downloads,
- project metrics,
- Linux/WSL local viewer launch.

## Data Layout

Important paths:

- `data/videos/<scene>.<ext>`: source video.
- `data/frames_videos/<scene>.jpg`: dashboard thumbnail.
- `jobs/segmentation/<scene>_job.json`: SAM 2 job generated by bbox selection.
- `data/masks/<scene>/`: predicted masks.
- `data/GT/<scene>/`: optional segmentation reference data.
- `data/3dgs/<scene>/colmap/`: COLMAP working data.
- `data/3dgs/<scene>/gs/source/`: normalized 3DGS input dataset.
- `data/3dgs/<scene>/gs/model/`: stable 3DGS model directory.
- `data/3dgs/<scene>/metrics/`: COLMAP, 3DGS and SuGaR metric summaries.
- `data/sugar_output/<scene>/`: SuGaR output folders.
- `data/metrics/segmentation/<scene>/`: SAM 2 mask evaluation reports.
- `logs/<scene>/`: pipeline and viewer logs.

## Presets

Presets are defined in `scripts/pipeline_presets.py` and reused by the script/backend/frontend flow.

- `fast`: quick validation, frame step 4, 1000 3DGS iterations, skips SuGaR by default.
- `balanced`: normal default, frame step 2, 7000 3DGS iterations, medium SuGaR.
- `quality`: slower final run, frame step 1, 30000 3DGS iterations, high/long SuGaR.

Use `fast` for a first tutor/demo run.

## Full Pipeline

The main orchestrator is `scripts/run_full_pipeline.py`.

Typical command:

```bash
python scripts/run_full_pipeline.py   --video videos/<scene>.mp4   --scene-name <scene>   --preset fast
```

The web backend launches this script in the background and stores web metadata in:

```text
logs/<scene>/<run_name>/web_pipeline_run.json
```

The pipeline manifest is written to:

```text
logs/<scene>/<run_name>/full_pipeline_manifest.json
```

Each stage writes a log file that the web polls for live output.

## Stage Scripts

### `scripts/bootstrap_checkpoints.py`

Downloads SAM 2.1 checkpoints into `models/sam2`.

Default checkpoint used by the web/presets:

```bash
docker compose run --rm sam2-seg python /app/scripts/bootstrap_checkpoints.py --checkpoint sam2.1_hiera_small
```

Supported values:

- `sam2.1_hiera_tiny`
- `sam2.1_hiera_small`
- `sam2.1_hiera_base_plus`
- `sam2.1_hiera_large`
- `all`

Example using the large checkpoint:

```bash
docker compose run --rm sam2-seg python /app/scripts/bootstrap_checkpoints.py --checkpoint sam2.1_hiera_large
```

Force a redownload if the file already exists:

```bash
docker compose run --rm sam2-seg python /app/scripts/bootstrap_checkpoints.py --checkpoint sam2.1_hiera_large --force
```

### `scripts/select_bbox.py`

Opens an interactive frame selector and writes a segmentation job.

```bash
python scripts/select_bbox.py --video videos/example.mp4 --frame-index 0
```

Outputs:

- `jobs/segmentation/<scene>_job.json`
- optional bbox preview under `data/masks/`

### `scripts/segment_video.py`

Runs SAM 2 video propagation from a job JSON.

```bash
docker compose run --rm sam2-seg python /app/scripts/segment_video.py --job /jobs/segmentation/<scene>_job.json
```

Outputs masks and `manifest.json` under `data/masks/<scene>/`.

### `scripts/evaluate_segmentation_masks.py`

Compares predicted masks with reference masks under `data/GT/<scene>/`.

Expected reference layout:

```text
data/GT/<scene>/masks_gt/000001.png
```

Run:

```bash
python scripts/evaluate_segmentation_masks.py --scene-name <scene>
```

Metrics include IoU/Jaccard, Dice/F1, precision, recall, specificity, pixel accuracy, boundary F-score and video J&F.

### `scripts/prepare_3dgs_dataset.py`

Builds the COLMAP/3DGS dataset from the video, job and masks.

```bash
python scripts/prepare_3dgs_dataset.py --job jobs/segmentation/<scene>_job.json --frame-step 2
```

Important: `--frame-step 1` processes every frame. Zero is invalid.

Outputs:

- `data/3dgs/<scene>/colmap/images`
- `data/3dgs/<scene>/colmap/masks`
- `data/3dgs/<scene>/gs/images`
- `data/3dgs/<scene>/gs/masks`
- `data/3dgs/<scene>/dataset_manifest.json`

### `scripts/run_colmap_pipeline.py`

Runs COLMAP and prepares `gs/source`.

```bash
python scripts/run_colmap_pipeline.py --scene-dir 3dgs/<scene> --single-camera --matcher sequential
```

Useful options:

```bash
python scripts/run_colmap_pipeline.py --scene-dir 3dgs/<scene> --matcher exhaustive
python scripts/run_colmap_pipeline.py --scene-dir 3dgs/<scene> --use-colmap-masks
python scripts/run_colmap_pipeline.py --scene-dir 3dgs/<scene> --no-use-gpu
```

For video, `--matcher sequential` and `--single-camera` are usually preferred.

### `scripts/train_3dgs.py`

Runs official 3DGS training in Docker.

```bash
python scripts/train_3dgs.py --scene-dir 3dgs/<scene> --iterations 7000
```

Default model output:

```text
data/3dgs/<scene>/gs/model
```

Use `--mask-loss` when training on original RGB images with aligned masks.

### `scripts/evaluate_3dgs_masked_metrics.py`

Evaluates a trained 3DGS model with both full-image and object-masked metrics:

```bash
python scripts/evaluate_3dgs_masked_metrics.py --scene-dir 3dgs/<scene> --model-dir 3dgs/<scene>/gs/model --split both
```

Metrics include L1, PSNR, SSIM and LPIPS. The report is written to:

```text
data/3dgs/<scene>/metrics/masked_3dgs/latest.json
```

When `run_full_pipeline.py --metrics` is used, this script runs automatically after 3DGS training.

### `scripts/estimate_sugar_bbox.py`

Estimates a 3D foreground bounding box for SuGaR from COLMAP points and masks.

```bash
python scripts/estimate_sugar_bbox.py --scene-dir 3dgs/<scene>
```

Output:

```text
data/3dgs/<scene>/sugar_bbox_estimate.json
```

### `scripts/train_sugar.py`

Runs SuGaR on top of the 3DGS/COLMAP dataset.

```bash
python scripts/train_sugar.py --scene-dir 3dgs/<scene>
```

Default SuGaR output:

```text
data/sugar_output/<scene>/
```

SuGaR usually expects a 3DGS model containing at least `point_cloud/iteration_7000/point_cloud.ply` unless using from-scratch options.

### `scripts/open_3dgs_viewer.sh`

Opens the Linux/WSL Docker SIBR viewer for a trained 3DGS scene.

```bash
scripts/open_3dgs_viewer.sh --scene-dir 3dgs/<scene>
```

Useful options:

```bash
scripts/open_3dgs_viewer.sh --scene-dir 3dgs/<scene> --iteration 7000
scripts/open_3dgs_viewer.sh --scene-dir 3dgs/<scene> --load-images
scripts/open_3dgs_viewer.sh --scene-dir 3dgs/<scene> --no-interop
scripts/open_3dgs_viewer.sh --scene-dir 3dgs/<scene> --print-only
```

On WSL, the script automatically adds `--no_interop` to avoid CUDA/OpenGL interop warnings.

### `scripts/open_sugar_viewer.sh`

Creates a temporary viewer-compatible model wrapper for a refined SuGaR `.ply`, then opens the same SIBR viewer.

```bash
scripts/open_sugar_viewer.sh   --ply-path sugar_output/<scene>/refined_ply/source/<model>.ply   --source-dir 3dgs/<scene>/gs/source
```

Temporary wrappers are written under:

```text
data/sugar_output/viewer/
```

### Utility Scripts

- `scripts/trim_video.py`: trim a source video before creating a scene.
- `scripts/pipeline_manifest.py`: shared manifest helpers for the full pipeline.
- `scripts/pipeline_presets.py`: shared preset definitions.
- `scripts/sam2_common.py`: common path validation and SAM 2 job helpers.
- `scripts/open_3dgs_viewer.ps1`, `scripts/open_sugar_viewer.ps1`, `scripts/install_3dgs_viewer.ps1`: legacy Windows viewer helpers.

## Common Web Workflows

### Quick Demo

1. Build containers.
2. Start backend and frontend.
3. Create a project from a short video.
4. Run preset `Fast`.
5. Open 3DGS viewer or download the 3DGS PLY.

### Full Reconstruction

1. Run preset `Balanced` or `Quality`.
2. Keep 3DGS iterations at 7000 or above if SuGaR will be used.
3. Inspect logs and metrics.
4. Download PLY/OBJ artifacts or open local viewers.

### Advanced Stage Runs

The advanced panel can run:

- full pipeline,
- a single stage,
- custom ordered stages.

Examples:

- Run until 3DGS: bbox, segmentation, dataset, COLMAP, 3DGS.
- Segmentation + prepare dataset: only masks and dataset rebuild.
- SuGaR from existing 3DGS: only `train_sugar`.
- Metrics-only: reuse existing outputs.

## Troubleshooting

### Docker Cannot See The GPU

Run:

```bash
docker run --rm --gpus all nvidia/cuda:12.4.1-base-ubuntu22.04 nvidia-smi
```

If this fails, fix NVIDIA driver/Docker GPU integration first.

### Viewer Does Not Open

Check:

```bash
echo $DISPLAY
docker compose build viewer
```

On native Linux/X11:

```bash
xhost +local:docker
```

On WSL, prefer WSLg and let the script use `--no_interop` automatically.

### Permission Errors When Clearing Data

Artifacts created by older root containers may need ownership repair:

```bash
sudo chown -R "$(id -u):$(id -g)" data jobs logs models
```

### Frontend Cannot Find Node

Install Node inside Linux/WSL and run `npm install` there. Do not mix Windows Node with WSL `node_modules`.
